## 0. 本课题对数据集的硬指标

两阶段方案拆开看，两个阶段的需求完全不同：

| | 第一阶段：画框定位 | 第二阶段：框内细分类 |
|---|---|---|
| 任务类型 | **目标检测** | **图像分类** |
| 必需 | **目标框标注** | 类别标签 |
| 必需 | **健康类负样本**（否则"健康/病害"学不出来） | 病害类别要够细 |
| 规模要求 | 中等即可（微调 COCO 预训练模型） | **越大越好** |

**关键洞察**：这两个阶段**不需要用同一个数据集**。规模问题只压在第一阶段；
第二阶段吃数据量，可以另找纯分类的大数据集（PlantVillage 等）。
**所以第 0 节的两个硬指标——"有框"+"有健康类"——才是筛选数据集的第一道筛子。**

### 2.4 ⚠️ 数字三方打架 —— 引用时必须注明来源

| 来源 | 图数 | 框数 | 类数 |
|---|---|---|---|
| 论文原文（CoDS-COMAD 2020） | 2,598 | 9,216 | 27 |
| **官方 CSV（我实算）** | **2,565** | **8,921** | **29** |
| Roboflow 改进版 | 2,569 | 8,851 | 30 |

论文口径是「13 物种 / 27 类（**17 病 + 10 健康**）」；CSV 里实际有 29 类（多了 `Potato leaf`
和 `Tomato two spotted spider mites leaf` —— 后者因少于 50 张被论文剔除）。
**写论文时写清用的是哪个口径**，别硬凑一个自洽的数字。

### 2.5 数据质量坑（全部实测）

| 问题 | 数量 | 影响 |
|---|---|---|
| 类别极度不均衡 | 最多 `Blueberry leaf` 849 框，最少 `Tomato two spotted spider mites leaf` **2 框** | 直接伤二分类精度 |
| **官方 test 集极小** | 236 图 / 452 框；`Corn Gray leaf spot` 全 test 仅 **4 框** | **不要直接用官方 test 报指标**，自己重做分层划分 |
| **同一文件名带两个互斥标签** | train 内 **20 个**文件名 | 污染二分类标签，训练前必须人工裁定或去重 |
| CSV 里 `width`/`height` = 0 | **4 行** | 归一化时会**除零** |
| `Potato leaf`（被当健康类） | 仅 11 框，且 3 张图文件名分别是 `0042241.jpg`、`21-late blight-early symptoms potato.jpg`、`1200px-Late_blight_on_potato_leaf_2.jpg` | **文件名本身就是晚疫病** → 当健康样本是错误标签 |
| 类名不规范 | `Soyabean`（拼写错）、`grape` 全小写、`Corn`（植物学应作 Maize）、大小写混用 | 跨数据集映射时必须显式归一化 |
| TRAIN/TEST 文件名重复 | 26 个 | 自定义划分时注意 |

### 2.6 框是「叶片级」，不是「病斑级」

论文原话：

> "we used the LabelImg tool to make the **bounding boxes around the leaves**"
> "we made sure that **the entire leaf should be present inside the box**"

**这直接影响你的任务定义**：应该写成「**病叶定位 + 健康叶判别**」，
**不能写「病斑检测 / 病灶定位」**。答辩时这两个说法会被追问。

### 2.7 方案里最幸运的一点

检测版的框 = 一整片叶子；分类版那 2,578 张裁剪图 = **正是按这些框裁出来的**。
也就是说：**推理时用 YOLO 框裁出来的图，和分类模型训练时看到的图是同一分布** ——
这个两阶段方案的"训推域对齐"问题天然不存在。
这是极少数同时提供叶片级框**和**对应裁剪分类图的公开数据集。

## 3. 为什么 IP102 / Pest24 / AgriPest 全部不合格

**"害虫检测"和"病害检测"是两件完全不同的事。** 这三个的数据集设计目标都是
**定位并计数昆虫个体**，框打在虫子上，既不是叶片级也不是病斑级。

我从 CVPR 2019 的 IP102 原文 PDF 逐句核对过（不是转述）：

```
"we annotate about 19,000 images with bounding boxes for object detection"
"For the task of object detection, there are totally 18,983 annotated images"
"We split those images containing bounding box annotations into 15,178 and 3,798 images
 as training and testing sets, respectively"
"The experts label the bounding boxes of insect pests following the format of Pascal VOC"
```

全文 grep `healthy` → **0 次命中**。102 个类名（从官方 `classes.txt` 拉取）逐条看过：

```
1 rice leaf roller   2 rice leaf caterpillar   23 corn borer   25 aphids
55 Thrips  102 Cicadellidae  ... （102/102 全是害虫物种）
```

**零病害、零健康类。**

| 数据集 | 状态 |
|---|---|
| IP102 | 只有 25% 的图有框；标注不在 GitHub 仓库里（仓库只有 README + classes.txt + 预训练模型），只能云盘整包下载 |
| Pest24 | 官方站 `aisys.iim.ac.cn` 实测不可达（curl HTTP 000） |
| AgriPest | 论文声称 `github.com/liuliu66/AgriPest`，**后台核查报 404**；⚠️ 我自己复查时撞上 GitHub API 限流（403 rate limit）和网络不通，**未能独立确认**，请本地再验一次 |

**一句话**：想用这三个，必须把课题改成"虫害检测"。对"叶片病害"课题，它们连备选都算不上。

## 4. 不存在的东西（这条本身很重要）

> **目前不存在同时满足「>1 万图 + 有检测框 + 含健康类 + 有正式论文」的大田作物叶部病害数据集。**

- 规模大的（PlantVillage 54k、PDDD 40 万、DLCPD-25 22 万）**全是整图分类、没有框**
- 有框又有健康类的（PlantDoc、FieldPlant、Multi-Crop）**都不大**

**这个"空白"可以写成你论文的 motivation**：
「现有唯一对口的叶片病害检测集仅 2.6k 张」，然后引出你的工作。

## 5. 三个推荐方案

### 方案 A（最稳，推荐）：以 PlantDoc 为主线

**理由**：它是唯一同时满足「叶片级框 + 明确的健康类 + 免登录 + 可只拉 CSV + 有正式论文 + CC BY 4.0」的数据集。

- 缺点：规模小（2.6k 图 / 8.9k 框）
- 应对：① 从 COCO 预训练的 YOLOv8 微调；② 做数据增强；③ 把规模小写成 motivation

### 方案 B（上规模）：PlantDoc + FieldPlant ≈ 7.8k 图

两者都是**叶片级**、都有**健康类**、作物有重叠（corn / tomato），可统一到 YOLO 格式。

- **FieldPlant**（Moupojou et al., IEEE Access 11:35398, 2023）：
  5,170 图 / 8,629 个叶片框 / 27 类，作物是 **corn、cassava、tomato**（真正的大田作物），
  有 `Cassava Healthy` / `Corn Healthy` / `Tomato Healthy`
- ⚠️ 已知缺陷：**部分类的框几乎覆盖整张图**，做检测意义有限，用前必须清洗
- 这是**唯一「有论文背书 + 有健康类」的扩规模路径**

### 方案 C（激进，上 1 万图）：Multi-Crop Disease Dataset

Mendeley DOI `10.17632/6243z8r6t6.1`，我实测该页面 HTTP 200，原文含
`over 23,000 images`（出现 5 次）、`Healthy`、`YOLO format`，CC BY 4.0。
5 作物：Banana、Chilli、Radish、Groundnut、Cauliflower。

**三条风险必须先自验**：
1. **没有论文**，只能引 Mendeley DOI
2. **30+ 类名未公开**，健康类的确切命名未知
3. 描述里框是标 `disease-affected regions`，**疑似病斑级**而非叶片级，与 PlantDoc 不一致

→ **建议先下载 1 个作物子集验证再决定是否写进论文。**

### 明确不要做

- ❌ 不要把 IP102 / Pest24 / AgriPest 当病害集用
- ❌ 不要引用"7,000 张水稻病害检测数据集"这类流传于中文博客但**无 DOI、无仓库、无出处**的数字
- ❌ 不要指望 PDD271（不公开）、AgriPest（链接已死）
- ⚠️ PlantSeg 量大类多，但**非商用许可 + 分割掩码**，转框有精度损失，适合当预训练/辅助，不适合当唯一主集

## 6.5 专项核查：有没有带「光照元数据」的数据集？

> **背景**：研究问题改成跨光照域泛化后，最理想的是一条**现成的光照标签**，
> 这样就不用自己训练光照分类器（也就绕开了标签噪声的陷阱）。
> 本节是对这个问题的专项核查结论。

### 结论：**不存在**带可信光照标注的公开叶片病害数据集

点名的 5 个候选，**元数据文件都被实际下载并核对过列名**：

| 数据集 | 元数据情况 |
|---|---|
| **PlantDoc** | 标签文件列名实测为 `filename,width,height,class,xmin,ymin,xmax,ymax` —— **无 time/date/location/weather/lighting**。而且它是**网络爬取**的，**根本不存在真实采集元数据** |
| **FieldPlant** | 托管在 Roboflow，GitHub 仓库只有模型代码。采集时间/地点**只存在于论文 Table 2 的聚合计数**，不是逐图字段 |
| **Multi-Crop** | DataCite 描述里有 "Covers real-world variations in **lighting**..." —— 但这是**数据集级别的定性声明，不是逐图标签** |
| **PlantWild** | 图文多模态数据集，附带的是 GPT 生成的类别文本描述，**无采集元数据** |
| **PaddyDoctor** | 逐图元数据只有 `variety`（品种）和 `age`（叶龄），**无时间/天气/光照/GPS** |

### ⚠️ 重点案例：GVLiD —— 纸面上完美契合，但**元数据与图片不符**

GVLiD（葡萄叶病害，Scientific Data 2026，DOI `10.1038/s41597-026-07431-9`）
在论文里声称：

> "In situ images were taken in the vineyard under different lighting conditions,
> including **sunny, overcast, shaded, and dusk**."
> "Metadata fields include vineyard ID, GPS coordinates, capture time,
> **lighting conditions**, weather conditions, device specifications..."

它的 `metadata.json` 里**确实有逐图的 `Lighting` 字段**（3 类各约 1,100 张），看起来就是为这个课题准备的。

**但实测发现这份元数据与真实图片对不上：**

| | metadata.json 声称 | **图片真实 EXIF** |
|---|---|---|
| 拍摄日期 | `2023-06-15`（**3,477 条全部同一天**） | **`2024-10-27`** |
| 设备型号 | `Redmi Note 10 5G`（**100%**） | **`samsung SM-A037F`** |
| 论文声称的采集期 | 2023 年 7–11 月 | 与上面两个都矛盾 |

**三条佐证**：

1. **日期全部相同**：3,477 条 `Time_of_Capture` 无一例外都是 `2023-06-15`，
   小时按 7,8,9,10,12,13,14,15,17,18,19,20 规律循环（**恰好缺 11 点和 16 点**）
2. **设备型号完全不符**：元数据 100% 是红米，EXIF 实测是三星；
   论文还说用了**两台**设备（Samsung S21 Ultra + Redmi Note 10 5G），**三方各说各话**
3. **标签与图像内容不相关**：按 `Lighting` 分组的平均亮度，
   组间极差（9.3）**小于**组内标准差（15.4）；
   抽样量从 18 张扩到 55 张时，"最亮的那一类"**直接反转** —— 典型的"标签是噪声"

**而且 EXIF 时刻全部落在 `11:36–12:03` 这半小时内** ——
半小时内不可能同时存在 sunny / overcast / partly cloudy 三种真实光照域。

> **结论：GVLiD 的 `Lighting` / `Weather` / `Time_of_Capture` / `GPS` / `Device` 字段
> 极可能是发布时程序化生成的，不对应真实采集条件。**
> **不要拿它做光照域实验**，否则域划分是随机的，会得到"没有域间隙"的假结论。
>
> **但这个负结果本身有价值**，可以写进论文：
> *"我们核查了 GVLiD 的元数据，发现其 Lighting 标签与图像 EXIF 不一致
> （日期差 16 个月、设备型号不符），不具备作为光照域基准的效力。"*

### 其他线索（概念上有先例，但拿不到数据）

**⚠️ 一处必须纠正的传言**：有说法称 TOM2024 的文件名是"Unix 毫秒时间戳"
（把 `1660552830471.jpg` 解成 2022-08-15）。**但 TOM2024 原文明确写着这两个数字段是
"randomly generated"**，用于保证文件名唯一。**当时间戳用是没有依据的**——数值巧合而已。

### 这对选型意味着什么

**"没有现成的光照域标签" 这件事本身就是一个可以写进论文的研究空白**，
而且它是**可论证的**（上面每个候选都有实测证据）。

**唯一的替代路径**：用**合成光照迁移**自己构造受控的光照域
（即 `实验设计梳理.md` 里的 **S2 方案**）。这条路**可控、可复现、且确实没人做过**。
